## Architecture, lifecycle and failure boundaries

Master agents propose structured data through read-only, provider-neutral adapters. Core independently validates structure, readiness, sourced additions, mutation classification and current policy. Agents do not certify completion. SQLite retains authoritative intent, runtime state, decisions, revisions and events; SPEC.md and ROADMAP.md are inspectable projections, never independent mutation authority. No editor dependency, UI change, production dependency, new execution state, schema migration, or phase tag was introduced.

The audit followed generated/supplied roadmaps into initial persistence, runtime scheduling, task packets, the serial phase lifecycle, Master approval/proposal resolution, and portable synchronization. Initial service persistence requires planning state and empty runtime storage. The lower-level database initializer retains its existing explicit-fixture/import mode; normal service initialization requests atomic runtime materialization. Failed validation/authorization does not install a roadmap mutation. SQLite failures roll back all authoritative changes. Portable failure after commit is an explicit durable-outcome-plus-sync-failure result, so callers must not replay the accepted mutation.

Current execution uses ordered phases and dependency-driven tasks. Mutations may change inactive tasks during a RUNNING phase; the executor refreshes the graph at task boundaries and immediately rechecks completion before phase validation. Active or unfinished attempts, validating phase snapshots, completed promises and historical identity remain protected. Superseded inactive nonterminal tasks are cancelled centrally and transactionally, retaining their audit/attempt history and any actual outstanding user-decision gate.

## Confirmed findings and resolutions

1. **Resolved — canonical roadmap mutations left runtime scheduling data stale.** Add/split/reorder/dependency/acceptance/detail/phase changes updated JSON but not task/phase rows. Scheduler and task packets then rejected otherwise accepted mutations. Initial persistence now materializes runtime rows and mutations reconcile positions, titles, criteria and dependency edges in the same transaction as canonical/revision/proposal/event writes. All targets precede edge insertion. Regressions consume mutated state through scheduler and task packets after database reopen, and prove event-insertion failures roll everything back.

2. **Resolved — lifecycle boundaries and cached phase snapshots did not protect or observe roadmap changes.** Direct mutation could change active work, historical promises, or phase ordering; a captured phase task list could omit newly accepted work. The final implementation rejects active/unfinished-attempt changes, preserves completed promises and phase positions, protects validation/approval snapshots, and refreshes phase work between tasks. A real Core phase-lifecycle regression inserts a third task after the second completes and proves all three execute and reach phase validation. The first overly broad repair blocked legitimate running-phase steering; the full suite exposed that regression, and it was corrected before release. Inactive user-wait supersession now performs audited cancellation; failed event persistence restores the previous wait state and roadmap. Historical task/phase deletion or cross-phase relocation fails closed instead of deleting evidence.

3. **Resolved — alternate mutation operations bypassed acceptance policy and dependencies.** A MINOR split could discard source acceptance promises and incoming dependencies; changing expected validators could silently remove validation obligations under SIGNIFICANT policy. Splits now inherit source dependencies and become SCOPE when required acceptance/validator promises disappear. Removing validator categories through architecture details also becomes SCOPE. Promise-preserving splits remain MINOR. Existing policy presets and intentional significant-change overrides are preserved.

4. **Resolved — approval evidence was insufficiently bound to the approved change.** Any active user decision could authorize a direct scope mutation, and supplied proposal content could be substituted for a stored approved proposal. Direct approvals now bind project, revision, exact before snapshot and operations through the preview category, with active user-decision and timestamp checks. Master proposals must equal their authoritative stored record before approval can be consumed. Tests reject unrelated decisions, different operations, stale approval replay and forged proposal contents, and retain successful inspected approvals.

5. **Resolved — graph-valid plans could be impossible to execute or inadequately validate.** Acyclic tasks could depend on a later phase or on a non-executable task, preventing serial phase progression. Optional phases with executable work could omit completion criteria. The shared schema rejects those plans with task/phase-specific errors. Initial persistence also repeats specification readiness and requires planning state, preventing direct persistence from bypassing critical questions or rewriting a running project.

6. **Resolved — roadmap provider output schema omitted a required property declaration.** `supersededByTaskIds` was declared in the provider schema but missing from `required`; the Codex adapter transmits that schema unchanged. OpenAI's [Structured Outputs contract](https://developers.openai.com/api/docs/guides/structured-outputs#all-fields-must-be-required) requires all declared fields. The provider schema now requires the array, the initial prompt asks for an empty array, and a recursive regression verifies both planning schemas. Existing persisted version 1 tasks without the optional field remain readable. No paid/live call is claimed as evidence.

7. **Resolved — renderer-produced documents failed their own round-trip for literal canonical syntax.** User text containing canonical delimiter examples created duplicate apparent blocks in SPEC.md or ROADMAP.md. Readable prose now escapes comment openers while canonical JSON preserves every original byte. Both document round-trip regressions pass; malformed/duplicate external canonical blocks still fail closed.

8. **Resolved — answered interview IDs could be resurrected after later batches or restart.** Only currently open IDs were remembered. New answer decisions now persist an optional `questionId`; schema validation rejects duplicate/answered-open IDs, and proposals check both current and previously answered IDs. A multi-batch, portable-round-trip/restart regression rejects reuse. Exact answers and existing legacy records remain preserved.

9. **Resolved — direct mutation metadata bypassed durable-history redaction.** The permission service redacted its own copy, but direct mutation actor/rationale/session/approval metadata remained raw in revisions. The mutation boundary now redacts before constructing durable revision/event data. A regression inspects the stored revision history for synthetic secret sentinels.

10. **Resolved — cross-project runtime ID collisions lacked actionable handling at materialization.** Runtime phase/task IDs are global keys, although graph validation checks one plan at a time. A preflight now names collisions with another project and asks for project-qualified stable IDs; the entire initial write rolls back, preserving both projects. Core never silently renames an inspected plan or adopts another project's rows.

No concrete omitted requirement in the reviewed sample/current flows remains established.
- Version 1 specifications written by older builds may lack provenance for already answered question IDs. Those discarded IDs cannot be reconstructed reliably. New answers retain them durably; older data remains readable. Downgrading to an older binary that rejects new optional fields is not guaranteed.
- Global runtime IDs require project-qualified identifiers when plans coexist. Collisions now fail atomically with guidance; automatic renaming was deliberately avoided to preserve stable inspected IDs.
- Graphs previously accepted despite impossible phase dependencies now fail closed until corrected. Historical phase/task identity and completed promises are intentionally not rewritten to make a mutation succeed. Portable human-edit conflicts still require resolution; they are surfaced without overwriting user content.
- Only current-state PASS reports for Phases 1–3 existed before this audit. Historical completion of Phases 5–9 is not equivalent to current-state audit PASS. The separately requested whole-Core integration audit remains deferred until Phases 1–9 have individually passed; it was not started, and no other phase was audited as an independent release scope here.
